# LockCRM

Личная CRM для контактов людей, которых знаю лично.

## Как запустить

### Что нужно установить

- Node.js (LTS) и pnpm
- Docker Desktop
- OpenSpec - для работы над фичами: `npm install -g @fission-ai/openspec@latest`. Требования лежат в `openspec/`, команды `/opsx:*` - в Claude Code

### База данных и почтовая заглушка (Docker)

1. Если файла `.env` ещё нет — скопируйте `.env.example` в `.env` и заполните значения:
   - база: имя пользователя, пароль, название базы, порт `5432`, строка подключения `DATABASE_URL`;
   - вход: `BETTER_AUTH_SECRET` — случайная строка от 32 символов (получить: `openssl rand -base64 32`), `BETTER_AUTH_URL=http://localhost:3000`, `SMTP_URL=smtp://127.0.0.1:1025`, `MAIL_FROM=noreply@example.com`;
   - `OWNER_EMAIL` — ваша почта, см. раздел «Почта владельца» ниже;
   - `MAILPIT_URL=http://127.0.0.1:8025` — для автотестов.
2. Запустите Docker Desktop.
3. В папке проекта выполните:

   ```
   docker compose up -d
   ```

   Запустятся PostgreSQL и Mailpit — почтовая заглушка: письма приложения не уходят в интернет, а остаются в ней.

4. Проверить, что всё работает:

   ```
   docker compose ps
   ```

   В колонке `STATUS` у `postgres` и `mailpit` должно быть `healthy`. Письма видны на http://localhost:8025.

Остановить: `docker compose stop`. Данные базы при этом сохраняются.

### Первый запуск приложения

Один раз, в папке проекта:

```
pnpm install
pnpm db:migrate
```

`pnpm db:migrate` создаёт в базе таблицы. Повторный запуск безопасен: уже применённые изменения он пропускает.

Тестовые данные (1000 вымышленных контактов с заметками, у трети задана частота общения — поэтому на главной сразу виден блок «Пора связаться»), по желанию:

```
pnpm db:seed
```

Контакты создаются у пользователя с почтой `OWNER_EMAIL`, поэтому она должна быть в `.env`, а пользователь должен уже быть в базе: `OWNER_EMAIL` была задана при `pnpm db:migrate`, или вы один раз вошли под этой почтой. Скрипт работает, только если у этого пользователя нет контактов: если они есть, он ничего не меняет и ничего не удаляет.

### Почта владельца (`OWNER_EMAIL`)

До входа у приложения не было пользователей, а контакты, заметки и группы лежали в общей куче. При первой миграции с входом (`0004_users_and_owners`) все они достаются одному пользователю — владельцу, с почтой из `OWNER_EMAIL`. Ничего не теряется: количество и содержимое остаются прежними.

- Нужна один раз: пока в базе есть данные без владельца. Если данные есть, а `OWNER_EMAIL` не задана, `pnpm db:migrate` падает и ничего не меняет.
- На пустой базе (новый компьютер, CI) не нужна.
- В git её нет и быть не должно (репозиторий публичный): только в `.env` — на компьютере и на сервере.
- После переноса владелец — обычный пользователь, никаких особых прав у него нет. Настройка остаётся нужной для `pnpm db:seed`.
- Опечатка в почте: данные достанутся пользователю с чужой почтой. Исправить на сервере можно командой `update users set email = '<верная почта>' where email = '<неверная>'` в базе, ничего не теряется.

### Запуск приложения

```
pnpm build
pnpm start
```

Откройте в браузере: http://localhost:3000

Приложение доступно только с этого компьютера и открывается только после входа.

#### Как войти локально

1. Откройте http://localhost:3000 — видна страница «Вход в приложение».
2. Введите любую почту, например `test-a@example.com`, и нажмите «Получить ссылку для входа».
3. Откройте http://localhost:8025 — там письмо «Вход в Личную CRM». Нажмите в нём «Войти».
4. Вы внутри, в шапке ваша почта. Первый вход под новой почтой и есть регистрация: у такого пользователя пустой список и четыре готовые группы.

Чтобы увидеть данные, которые были до входа (или демо-данные), входите под почтой из `OWNER_EMAIL`.

#### Вход по паролю

Войти можно двумя способами: по ссылке из письма и по почте и паролю. Отдельной регистрации нет: первый вход всегда по ссылке, пароль задаётся уже внутри.

1. Войдите по ссылке, как написано выше, и нажмите на свою почту в шапке — откроется страница «Настройки».
2. В блоке «Задать пароль» введите пароль от 8 до 128 символов и нажмите «Сохранить пароль». На http://localhost:8025 придёт письмо «Пароль в Личной CRM изменён».
3. Нажмите «Выйти», на странице входа откройте вкладку «Почта и пароль», введите почту и пароль, нажмите «Войти». Браузер запомнит эту вкладку.

Забыли пароль: на вкладке «Почта и пароль» нажмите «Забыли пароль?». Письмо «Смена пароля в Личной CRM» со ссылкой на 15 минут придёт в Mailpit. Пользователь, у которого пароля ещё не было, так тоже может его задать.

#### Как сменить почту локально

Сменить почту можно, только если задан пароль.

1. В «Настройках» в блоке «Почта» введите новую почту и текущий пароль, нажмите «Сменить почту».
2. В Mailpit придут два письма: на новую почту — «Смена почты в Личной CRM» со ссылкой на 15 минут, на старую — уведомление «Запрошена смена почты в Личной CRM».
3. Откройте ссылку из письма на новую почту. Если на этом устройстве вход уже есть, откроются настройки и «Почта изменена». Если входа нет, откроется страница входа и «Почта изменена. Войдите с новой почтой.»

Если меняется почта из `OWNER_EMAIL`, обновите её в `.env` на компьютере и на сервере: иначе `pnpm db:seed` выдаст ошибку, что такого пользователя нет. На работу приложения это не влияет.

Остановить: нажмите `Ctrl + C` в окне, где запущено приложение, или закройте это окно.

Режим для разработки (изменения в коде видны сразу, но работает медленнее): `pnpm dev`.

## Как проверить, что всё работает

### Руками

1. Откройте http://localhost:3000 и войдите (см. «Как войти локально») — видно список ваших контактов и их количество.
2. Нажмите «Добавить контакт», впишите имя и нажмите «Добавить» — контакт появится в списке с пометкой «Новый».
3. Начните вводить его имя в строке поиска — в списке останется он один. Откройте его карточку.
4. Впишите заметку и нажмите «Добавить заметку». Обновите страницу (F5) — заметка на месте.
5. Вернитесь к списку. Поиск ищет везде: по имени, «Кто это», «Откуда знакомы», телефону, почте и заметкам. Слова запроса могут найтись в разных полях.
   - Впишите слово из только что добавленной заметки — контакт найдётся, под именем видна строка «Заметка: …» с выделенным словом.
   - На тестовых данных: «8 974 639 74 31» находит Григория Степанова по телефону (номер записан как «+7 974 639-74-31»), «Новосибирск Баранов» — Виктора Баранова по «Откуда знакомы».
   - Сузьте окно до ширины телефона и поищите по телефону или почте — под именем появится строка «Телефон: …» или «Почта: …».
6. Откройте тот же адрес в другом браузере и войдите под той же почтой — там те же контакты и та же заметка.
7. В карточке контакта нажмите «Удалить». В окне видно имя и сколько заметок удалится вместе с ним. «Отмена» — ничего не меняется. «Удалить» — открывается список, контакта в нём больше нет.
8. Напоминания «Пора связаться»:
   - В окне «Новый контакт» или «Изменить» выберите в поле «Как часто общаться», например, «Раз в неделю». В карточке под полем видно «Следующий раз — до …». Срок считается от последней заметки или нажатия «Связались», а если их не было — от дня, когда контакт добавлен.
   - На главной над поиском есть блок «Пора связаться» с теми, у кого срок уже прошёл, самые просроченные сверху. Если таких нет, блока нет. Пока в поиске есть запрос, блок скрыт.
   - Нажмите галочку у контакта: строка меняется на «Отметили общение» с кнопкой «Отменить» и через 5 секунд исчезает. «Отменить» возвращает строку, как была. Карточка при этом не открывается и заметка не появляется.
   - В карточке то же делает кнопка «Связались» (она есть, если задана частота): срок сдвигается, внизу на 5 секунд появляется «Отметили общение» с «Отменить». Новая заметка тоже сдвигает срок и убирает контакт из блока.
9. Вход и чужие данные — двумя почтами в двух браузерах (например, обычное и приватное окно):
   - Войдите как `test-a@example.com` в одном окне и добавьте контакт. В другом окне войдите как `test-b@example.com`: контакта первого нет ни в списке, ни в поиске, а его адрес в строке браузера открывает «Такого контакта нет».
   - Без входа любая страница ведёт на «Вход в приложение». Неверная почта (например, `anna@`) — под полем «Проверьте адрес почты».
   - Письмо: отправитель «Личная CRM», тема «Вход в Личную CRM», по порядку — «Чтобы войти…», кнопка «Войти», «Если вы не запрашивали вход…». Ссылка работает один раз: откройте её второй раз — «Ссылка устарела», в поле почта, кнопка «Отправить ссылку повторно» присылает новое письмо.
   - Четвёртое письмо на одну почту за 10 минут не уходит: «Слишком часто, попробуйте через несколько минут».
   - «Выйти» в шапке — страница входа, «Назад» в браузере не показывает контакты. В другом окне вы остаётесь внутри.
10. Вход по паролю и настройки (все письма — на http://localhost:8025):
    - Задайте пароль и войдите с ним (см. «Вход по паролю»). Неверный пароль, неизвестная почта и почта без пароля дают одно и то же: «Неверная почта или пароль».
    - Пять неверных паролей подряд: шестая попытка даже с верным паролем даёт «Слишком много попыток. Попробуйте через 15 минут или войдите по ссылке.» Вход по ссылке при этом работает.
    - «Забыли пароль?»: ссылка из второго письма работает, из первого — «Ссылка устарела». После нового пароля выходят все устройства, старый пароль больше не впускает.
    - «Сменить пароль» в настройках при входе в двух браузерах: этот остаётся внутри, второй после обновления страницы показывает вход.
    - В базе пароля нет: `pnpm db:studio`, таблица `accounts`, поле `password` начинается с `scrypt$`. В таблице `verifications` нет строки из ссылки в письме.

### Автоматически

Нужны запущенные Docker-контейнеры (`docker compose up -d`: база и Mailpit). Тесты Vitest не требуют запущенного приложения:

```
pnpm test
```

Они входят по настоящей ссылке из письма в Mailpit и ничего не мокают. Письма в них всегда идут в Mailpit, какие бы настройки ни стояли в `.env`.

Тесты в браузере: пока приложение запущено, выполните

```
pnpm test:e2e
```

Они проходят весь сценарий выше в Microsoft Edge и Google Chrome. Каждый файл тестов входит под своей уникальной почтой (`e2e-…@example.com`) и работает только с её данными, а в конце удаляет их вместе с этим пользователем — ваши контакты не трогаются.

Тесты идут на приложении, которое открыто по адресу http://localhost:3000, и сами ничего не пересобирают. После изменений в коде остановите приложение и запустите его заново (`pnpm build`, затем `pnpm start`), иначе тесты проверят старую версию.

### Проверки на GitHub (CI)

На каждый PR в `main` GitHub Actions запускает `.github/workflows/ci.yml`. В нём три проверки:

- `checks` — форматирование (Prettier), lint, типы TypeScript;
- `tests` — тесты Vitest и e2e-тесты Playwright на собранном приложении, отдельной пустой базе PostgreSQL и Mailpit (письма входа);
- `image` — сборка Docker-образа приложения (только сборка, образ никуда не отправляется).

`main` защищена: изменения попадают туда только через PR, и только когда все три проверки зелёные. PR вливается сам (squash), как только CI зелёный, если для него включено автовлитие.

Если упала проверка формата, выполните `pnpm format`, закоммитьте и отправьте изменения снова.

## Выкатка на сервер

Прототип работает на https://app.funkicrm.ru (сервер `157.22.207.202`, вход: `ssh crm`).

Вход по ссылке из письма: каждый входит под своей почтой и видит только свои контакты. Письма уходят через Resend (по SMTP, настройка `SMTP_URL`).

### Письма входа: домен и ключ Resend (делает человек, один раз)

1. В Resend добавьте домен отправителя (например, `mail.crm.funkicrm.ru`) и внесите у регистратора DNS-записи, которые Resend покажет (SPF, DKIM). Пока домен не подтверждён, письма могут попадать в спам или не уходить.
2. В Resend создайте ключ API (права только на отправку).
3. Адрес отправителя (`MAIL_FROM`) должен быть на подтверждённом домене, например `noreply@mail.crm.funkicrm.ru`.

### Как выкатить новую версию

Отправьте коммит в ветку `main` (`git push`). Дальше всё произойдёт само (`.github/workflows/deploy.yml`):

1. GitHub Actions собирает Docker-образ приложения и кладёт его в GHCR (хранилище образов GitHub). Тег образа — SHA коммита.
2. Копирует папку `deploy/` на сервер в `/srv/lockcrm/deploy` и запускает `deploy.sh`.
3. `deploy.sh` на сервере: скачивает образ → бэкап базы → разовый контейнер из того же образа применяет миграции → запускается новая версия → проверка `/health` (smoke) → удаляются старые образы, кроме текущего и предыдущего.

Если бэкап не снялся или миграции упали, новая версия не запускается и продолжает работать старая. Если smoke красный, выкатка считается упавшей, и GitHub присылает письмо. Автоматического отката нет.

### Как проверить

- Ход выкатки: вкладка **Actions** в репозитории на GitHub (или `gh run watch` в терминале).
- https://app.funkicrm.ru/health отвечает `{"status":"ok","version":"<SHA коммита>"}`. Версия совпадает с последним коммитом в `main` — значит, на сервере новая версия.

### Откат (только вручную)

```
ssh crm
bash /srv/lockcrm/deploy/rollback.sh
```

Запускает предыдущую версию приложения. Миграции базы при этом не откатываются.

**Выкатку, которая принесла вход (миграция `0004_users_and_owners`), откатывать нужно только вместе с базой.** У каждого контакта и группы теперь есть владелец, и прежняя версия приложения о нём не знает: она не сможет создать контакт. Порядок:

1. `bash /srv/lockcrm/deploy/rollback.sh` — прошлая версия приложения;
2. `bash /srv/lockcrm/deploy/restore.sh /srv/lockcrm/backups/<файл вида …_deploy_<прошлая версия>.dump>` — база из копии, снятой этой выкаткой перед миграциями.

Всё, что люди успели добавить после выкатки, при таком откате пропадёт: копия снята до неё.

**Выкатку, которая принесла вход по паролю (миграция `0005_login_password_attempts`), откатывать можно без восстановления базы.** Достаточно `rollback.sh`: прошлая версия не знает новую таблицу и не читает пароли. На время отката вход по паролю пропадёт, вход по ссылке останется. Заданные пароли сохранятся и снова заработают при возврате на новую версию. Уже сменённая почта останется новой: вход по ссылке работает с ней.

### Бэкапы базы

Каждая выкатка перед миграциями сохраняет бэкап базы в `/srv/lockcrm/backups`. Читать эти файлы может только владелец: в них личные данные.

Имя файла: дата и время, причина и версия приложения, которая работала в этот момент:

- `2026-11-04_11-30-00_deploy_<SHA>.dump` — снят выкаткой; `<SHA>` — версия **до** выкатки (при самой первой выкатке — `none`);
- `2026-11-04_12-00-00_restore_<SHA>.dump` — копия базы, которую restore снял перед заменой.

Хранятся последние 30 файлов, более старые удаляются сами.

Посмотреть список:

```
ssh crm
ls -lh /srv/lockcrm/backups
```

Скачать бэкап к себе на компьютер (в текущую папку):

```
scp crm:/srv/lockcrm/backups/<имя файла> .
```

### Восстановление базы из бэкапа (только вручную)

```
ssh crm
bash /srv/lockcrm/deploy/restore.sh /srv/lockcrm/backups/<имя файла>
```

1. Скрипт проверяет, что файл — настоящий бэкап, и показывает: какой файл, какую базу заменит, какая версия приложения работает. Пока ничего не изменено.
2. Ждёт ввода `yes`. Любой другой ответ — выход, ничего не меняется.
3. Останавливает приложение и снимает копию текущей базы (`..._restore_<SHA>.dump`). Если копия не снялась, приложение запускается обратно, база не тронута.
4. Удаляет базу, создаёт её заново пустой и загружает в неё бэкап.
5. Если бэкап снят на более старой версии, достраивает базу до текущей версии приложения (те же миграции, что при выкатке). Данные из бэкапа не меняются, новые поля у старых записей пустые.
6. Запускает приложение той же версии, что работала, и проверяет `/health`. Версия приложения не меняется.

В конце пишет, где лежит копия базы, какой она была до восстановления. Вернуть её можно тем же скриптом.

Если скрипт упал на шагах 4–6, приложение остаётся остановленным. Скрипт пишет, на каком шаге упал и какой командой вернуть базу, как была (из копии с шага 3).

| Пароли базы, ключи входа и почты, `OWNER_EMAIL` | `/srv/lockcrm/.env` (права 600, в git не попадает) |
| Скрипты выкатки | `/srv/lockcrm/deploy/` (копируются из репозитория при каждой выкатке) |
| История выкаток | `/srv/lockcrm/releases.log` (последняя строка — текущая версия) |
| Бэкапы базы | `/srv/lockcrm/backups/` (последние 30, читает только владелец) |
| Контейнеры | docker compose, проект `prod`: `db` (PostgreSQL), `app`, разовый `migrate` |

Посмотреть контейнеры: `docker ps`. Логи приложения: `docker logs prod-app-1`.

Тестовые данные на сервере (работает только с пустой базой, ничего не удаляет): `bash /srv/lockcrm/deploy/seed.sh`.

### Первая настройка сервера (уже сделана, нужна только для нового сервера)

1. `deploy/setup-server.sh` с sudo: даёт пользователю `crmapp` доступ к Docker, создаёт `/srv/lockcrm` и направляет nginx для `app.funkicrm.ru` в приложение.
2. Создать `/srv/lockcrm/.env` с правами 600:
   - база: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `DATABASE_URL=postgresql://USER:PASSWORD@db:5432/DB`;
   - вход: `BETTER_AUTH_SECRET` (сгенерировать на сервере: `openssl rand -base64 32`), `BETTER_AUTH_URL=https://app.funkicrm.ru`;
   - письма: `SMTP_URL=smtps://resend:<ключ Resend>@smtp.resend.com:465` (в нём ключ — это секрет), `MAIL_FROM=noreply@<подтверждённый в Resend домен>`;
   - `OWNER_EMAIL=<ваша почта>` — нужна для выкатки, которая приносит вход (см. «Почта владельца»); без неё миграция на базе с данными откатится, новая версия не запустится, продолжит работать старая.
3. В GitHub (Settings → Secrets and variables → Actions): секрет `DEPLOY_SSH_KEY` (приватный ключ деплоя; публичный — в `~/.ssh/authorized_keys` на сервере), переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS`.
