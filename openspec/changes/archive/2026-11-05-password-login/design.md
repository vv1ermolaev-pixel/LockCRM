# Design

## Context

Зачем — `proposal.md`; что должно получиться — `specs/password-login`, `specs/user-login` этого изменения.

Как сейчас:

- `src/lib/auth.ts`: `betterAuth()` с плагином magic link. Встроенный `rateLimit` выключен, потому что он не видит вызовы из server actions; вместо него лимит по IP в памяти в `hooks.before` (только для `/sign-in/magic-link`) и лимит писем в таблице `login_email_sends` внутри `sendMagicLink`
- Ссылки входа: в `verifications` лежит `magic-link:<хэш>`, код гасит старые ссылки по этому префиксу
- `src/components/login-form.tsx`: одна форма на `/login` и `/login/expired`, ошибки под полем, экран «Проверьте почту»
- Таблица `accounts` есть и пуста: magic link строк в ней не создаёт. Поле `accounts.password` уже есть в схеме
- У всех пользователей `email_verified = true`: и созданных ссылкой, и владельца из миграции `0004`
- Падения запросов уже не выводят значения в лог (`src/db/errors.ts`), логгер Better Auth — уровень `error`

Что выяснено по исходникам Better Auth (сверено с 1.7.17, задача 1.1):

- `emailAndPassword` даёт `/sign-in/email`, `/change-password`, `/request-password-reset`, `/reset-password`, серверный `setPassword`. Новых библиотек не нужно
- Для неизвестной почты вход тратит то же время на хэш, сообщение одно: `INVALID_EMAIL_OR_PASSWORD`. Запрос сброса отвечает одинаково, но письмо уходит только известной почте
- Сброс создаёт строку `accounts` с паролем, если её нет: «Забыли пароль?» подходит и тем, кто входил только по ссылке
- `disableSignUp: true` выключает регистрацию
- По умолчанию scrypt `N=2^14, r=16, p=1` и сравнение через `===`: это слабее рекомендации OWASP; настройки `password.hash/verify` позволяют заменить расчёт
- Токен сброса по умолчанию лежит открытым текстом; `verification.storeIdentifier` хэширует его
- Старые ссылки сброса при новом запросе не гаснут, лимита на почту нет
- `hooks.after` получает результат и при ошибке: `ctx.context.returned` содержит `APIError`
- `user.changeEmail` даёт `/change-email` и `/verify-email`. Без `sendChangeEmailConfirmation` письмо со ссылкой уходит сразу на новую почту. Для занятой почты ответ тот же, письмо не уходит. Токен — подписанная строка (JWT) без записи в базе, срок задаёт `emailVerification.expiresIn`. Если токен не подошёл, Better Auth ведёт на `callbackURL?error=…`. Старый адрес после смены не находится, поэтому повторный переход по ссылке даёт ошибку. Если в браузере вход другого пользователя — тоже ошибка. Если входа нет, почта меняется, а сессия не создаётся: это поведение появилось в 1.7.16 вместе с привязкой токена к пользователю (`userId`)
- `/change-email` не принимает пароль; `auth.api.verifyPassword` проверяет его только на сервере

## Goals / Non-Goals

**Goals:**

- Максимум готового Better Auth: своё только там, где его нет (лимиты по почте, гашение старых ссылок, параметры хэша, тексты)
- Все ограничения — на сервере и действуют и для форм, и для прямых запросов на `/api/auth/*`
- Ни один ответ, текст и заметная разница во времени не выдаёт, есть ли пользователь и задан ли у него пароль

**Non-Goals:**

- Замена хэша при входе у уже сохранённых паролей: параметры записаны в самом хэше, пересчёт можно добавить, когда параметры поменяются
- Защита от распределённого подбора с тысяч IP сверх лимита на почту
- Отдельный счётчик блокировок и письма о блокировке

## Decisions

### 1. Настройки Better Auth

В `betterAuth()` добавляется:

```ts
emailAndPassword: {
  enabled: true,
  disableSignUp: true,
  minPasswordLength: 8,
  maxPasswordLength: 128,
  resetPasswordTokenExpiresIn: 15 * MINUTE,
  revokeSessionsOnPasswordReset: true,
  password: { hash: hashPassword, verify: verifyPassword },
  sendResetPassword,
  onPasswordReset,
},
verification: { storeIdentifier: { default: "plain", overrides: { "reset-password": "hashed" } } },
user: { changeEmail: { enabled: true } },
emailVerification: { expiresIn: 15 * MINUTE, sendVerificationEmail: sendEmailChangeLink },
```

- `disableSignUp`: пользователей создаёт только первый вход по ссылке. Поэтому не нужны подтверждение почты при регистрации, состояние `email_verified = false` и защита от подставленного чужого пароля: пароль может задать только тот, кто уже доказал владение почтой
- `default: "plain"` оставляет строки magic link как есть: они уже хранят хэш сами, а код ищет их по префиксу. Общая настройка `"hashed"` сломала бы эту логику

Альтернатива — форма регистрации с `requireEmailVerification`: отвергнута владельцем.

### 2. Хэш пароля: scrypt с параметрами OWASP, `src/lib/password-hash.ts`

Свои `hashPassword` и `verifyPassword` на `node:crypto`, без новых библиотек:

- `scrypt`, `N=2^17`, `r=8`, `p=1`, ключ 32 байта — основная рекомендация OWASP Password Storage Cheat Sheet. `maxmem` задаётся явно: значение по умолчанию меньше
- Случайная соль 16 байт на каждый хэш
- Формат `scrypt$<N>$<r>$<p>$<соль>$<ключ>` (base64url): параметры записаны в строке, поэтому их можно поменять, и старые пароли продолжат проверяться
- Пароль перед расчётом проходит `normalize("NFKC")`: один и тот же пароль с разных устройств даёт один хэш
- Сравнение — `timingSafeEqual`; неверный формат строки — просто `false`
- Расчёт асинхронный, в пуле потоков libuv, и не блокирует сервер

Альтернативы:

- Настройки Better Auth по умолчанию — в 2–4 раза слабее рекомендации OWASP, и работает сравнение строк `===`
- Argon2id — первый выбор OWASP, но требует новую нативную библиотеку или экспериментальный API Node; scrypt OWASP тоже рекомендует, а формат хэша оставляет дорогу к переходу
- «Перец» (общий секрет сверху) — ещё один секрет, потеря которого запирает всех; отвергнут как лишний для этого приложения

### 3. Лимиты: `src/lib/login-limits.ts`, хуки Better Auth

Лимиты живут в хуках, потому что только они видят и server actions, и прямые запросы. Код лимитов выносится из `auth.ts` в отдельный файл.

**По IP.** Существующие `clientAddress` и `assertIpWithinLimit` (30 запросов в минуту, в памяти) работают для `/sign-in/magic-link`, `/sign-in/email`, `/request-password-reset`, `/reset-password`, `/change-password`, `/verify-email`. Счётчик один на все пути: важно ограничить поток с одного адреса, а не каждое действие.

**Попытки входа.** Новая таблица `login_password_attempts`. Функция `reservePasswordAttempt(email)` в транзакции:

1. `pg_advisory_xact_lock(hashtext('password:' || email))`
2. Удаляет строки старше 15 минут
3. Считает строки этой почты; 5 и больше — `APIError` 429 `TOO_MANY_PASSWORD_ATTEMPTS`, пароль не проверяется и память на хэш не тратится
4. Вставляет строку

Попытка записывается **до** проверки пароля, а удачная удаляет строки этой почты. Если бы запись шла после неудачи, 50 одновременных запросов успели бы проскочить лимит.

Пути:

- `hooks.before` для `/sign-in/email`: лимит IP → нормализация почты `loginEmailSchema` (неверная — 400) → `reservePasswordAttempt` → подмена `body.email`
- `hooks.after` для `/sign-in/email`: в `ctx.context.returned` нет ошибки → `clearPasswordAttempts(email)`
- `hooks.before` для `/change-password`: пользователь берётся из `getSessionFromCtx(ctx)`, резервируется попытка по его почте
- `hooks.after` для `/change-password`: успех → `clearPasswordAttempts`, погасить ссылки сброса, уведомление
- `onPasswordReset`: `clearPasswordAttempts`, уведомление

Встроенный `rateLimit` не подходит: считает только по IP и пути и не видит server actions. Блокировка в памяти не подходит: перезапуск сбрасывал бы защиту.

**Письма.** Из `sendMagicLink` выносится `assertWithinEmailLimit(tx, email)`: очистка и подсчёт в `login_email_sends`, блокировка по тому же ключу `hashtext(email)`, поэтому лимит для двух видов писем общий и одновременные запросы идут по очереди. `sendMagicLink` в остальном не меняется.

### 4. «Забыли пароль?»

`hooks.before` для `/request-password-reset`: лимит IP → `loginEmailSchema` → резервирование письма в `login_email_sends`. Резервирование идёт **до** того, как станет известно, есть ли пользователь: 429 приходит и для неизвестной почты, иначе сам лимит выдавал бы существующие адреса.

`sendResetPassword({ user, url, token })` ничего не ждёт: запускает фоновую задачу и сразу возвращается. Задача удаляет прежние ссылки сброса этого пользователя (`value = user.id`, кроме только что созданной — её хэш считается той же функцией, что у Better Auth) и отправляет письмо. Ошибка отправки пишется в лог только кодом.

Причина — время ответа: для известной почты шло бы письмо, для неизвестной нет, и разницу в секунду легко измерить; ошибка почтового сервиса тоже была бы только у известной почты. Цена — при сбое почты человек увидит «Проверьте почту» и не получит письма (см. Risks).

Server action `requestPasswordResetLink(formData)` в `src/app/login/actions.ts`: `loginEmailSchema`, `auth.api.requestPasswordReset({ body: { email, redirectTo: "/login/reset" }, headers })`, `rememberLoginEmail`. Для «Забыли текущий пароль?» — тот же запрос с почтой из сессии; разница только в тексте экрана: своя почта точно есть.

Ссылка в письме ведёт на `/api/auth/reset-password/<token>?callbackURL=/login/reset`: Better Auth проверяет токен и отправляет на `/login/reset?token=…` или `/login/reset?error=INVALID_TOKEN`.

### 5. Страница входа

- `pnpm dlx shadcn add tabs` — компонент на уже установленном `radix-ui`, новых зависимостей нет
- `src/components/login-panel.tsx` — клиентская карточка: заголовок, вкладки, общее состояние почты, переход в «Забыли пароль?» на месте формы без своего адреса. Почта не попадает в адрес страницы
- Из `LoginForm` выделяется внутренняя форма запроса письма: общая для вкладки ссылки, «Забыли пароль?», `/login/expired` и устаревшей ссылки сброса; у неё меняются action, подпись кнопки и текст экрана «Проверьте почту». Сам `LoginForm` с заголовком остаётся для страниц «Ссылка устарела»
- Вкладка пароля — `PasswordLoginForm`. Server action `signInWithPassword(formData)` вызывает `auth.api.signInEmail`; при успехе клиент делает `window.location.replace("/")` — как при выходе, полная загрузка
- `src/components/password-input.tsx` — поле с кнопкой-значком `EyeIcon`/`EyeOffIcon`, `autoComplete` приходит параметром: `current-password` или `new-password`
- Вкладки по порядку: «Вход по ссылке», «Почта и пароль»
- Запомненная вкладка — cookie `login_method` (`link` или `password`), `path=/login`, год. Нет cookie — открыта `link`. Ставится в браузере при переключении, читается на сервере в `page.tsx`, поэтому нужная вкладка сразу в первом HTML. localStorage дал бы мигание вкладки. Личных данных в ней нет, `httpOnly` не нужен
- `/login?password=changed` — сообщение «Пароль изменён. Войдите с новым паролем.», вкладка пароля

Ошибки action переводятся по коду `APIError`, как в `requestLoginLink`:

| Код | Текст |
| --- | --- |
| `INVALID_EMAIL_OR_PASSWORD`, `PASSWORD_TOO_LONG` при входе | «Неверная почта или пароль» |
| `TOO_MANY_PASSWORD_ATTEMPTS`, лимит IP на формах пароля | «Слишком много попыток. Попробуйте через 15 минут или войдите по ссылке.» |
| `TOO_MANY_LOGIN_EMAILS` на формах письма | «Слишком часто, попробуйте через несколько минут» |
| `INVALID_PASSWORD` при смене | «Неверный текущий пароль» |
| `INVALID_TOKEN` при сбросе | экран «Ссылка устарела» |

Проверка пароля при входе в форме — только «не пустой». Длина проверяется только для нового пароля: `passwordSchema` в `src/lib/validation.ts`, без `trim` — пробелы часть пароля.

### 6. Страница новой ссылки `/login/reset`

`src/app/login/reset/page.tsx` — серверная, без редиректа для вошедшего: человек мог открыть ссылку в браузере со старым входом, а сброс как раз нужен, если его вход под подозрением.

- Нет `token` или есть `error` → `LoginForm`: «Ссылка устарела», «Отправить ссылку повторно», почта из cookie `login_email`
- Есть `token` → `ResetPasswordForm`: поле «Новый пароль». Action `resetPassword(formData)` вызывает `auth.api.resetPassword({ body: { newPassword, token }, headers })`; успех → `window.location.replace("/login?password=changed")`; `INVALID_TOKEN` → тот же экран «Ссылка устарела»

Better Auth сам гасит токен, меняет пароль и удаляет сессии в одной транзакции.

### 7. Страница «Настройки»

`src/app/(app)/settings/page.tsx`: `requireUserId()`, `hasPassword(userId)` (`src/lib/password.ts`: строка `accounts` этого пользователя с `provider_id = 'credential'` и непустым паролем). Почта в шапке `src/app/(app)/layout.tsx` становится ссылкой на `/settings`, высота попадания не меньше 44 px; на узком экране она по-прежнему сжимается (`truncate`). Отдельной кнопки нет.

Actions в `src/app/(app)/settings/actions.ts`:

- `setFirstPassword(formData)`: `requireUserId`, `passwordSchema`, `auth.api.setPassword` — только серверный метод, по HTTP недоступен; затем уведомление. Хук `hooks.after` тут не срабатывает: у метода нет пути
- `changePassword(formData)`: `auth.api.changePassword({ body: { currentPassword, newPassword, revokeOtherSessions: true }, headers })`. Better Auth удаляет все сессии и создаёт новую для этого устройства; cookie обновляет `nextCookies()`
- `sendPasswordResetToMe()`: сброс на почту из сессии

После смены пароля Next.js перерисовывает страницу в том же запросе, и `headers()` отдаёт cookie уже удалённой сессии, а `cookies()` — новую. Поэтому `getCurrentUser` берёт cookie из `cookies()`: иначе человек улетал бы на главную без сообщения. Vitest этого не видит, шаг проверяет e2e.

Отзыв других сессий при смене не противоречит требованию «Выход только на этом устройстве»: оно про кнопку «Выйти», а смена пароля — как раз реакция на возможную кражу.

### 8. Письма: `src/lib/mail.ts`

Общая часть — разметка письма (абзац, необязательная кнопка, приписка) и отправка. Шаблоны: существующий вход (тексты не меняются, проверка в `login.test.ts`), `sendPasswordResetEmail(to, url)`, `sendPasswordChangedEmail(to)`, `sendEmailChangeLink(to, url)`, `sendEmailChangeNotice(to, newEmail)`. Новая почта в тексте письма экранируется той же `escapeHtml`.

Письма сброса, смены почты и уведомления уходят через `sendInBackground(job)`: ловит ошибку и пишет в лог только код, как в `sendMagicLink`. Письмо входа по-прежнему ждём: там ответ не зависит от существования пользователя.

### 9. Логи

- Пароль не проходит через параметры запросов к базе, только хэш
- Падения запросов уже закрыты `hideQueryValuesInErrors`, и новые запросы попадают под него сами
- Логгер Better Auth на уровне `error`: его `warn` с `User not found` не выводится
- Тест `login-logs.test.ts` расширяется: неверный пароль, блокировка, сбой почты, все три пути смены — в выводе нет пароля, хэша, ссылки и почты

### 10. Миграция

Новая схема: `login_password_attempts (id, email, attempted_at)`, индекс `(email, attempted_at)`. `pnpm db:generate` создаёт `0005_login_password_attempts.sql` (только `CREATE TABLE` и `CREATE INDEX`).

Что будет с существующей базой:

- Данные не меняются: миграция не трогает пользователей, контакты, группы и входы. Показывать её владельцу до merge по правилу о данных не требуется; она видна в PR
- Пустая таблица появляется в разовом контейнере миграций до старта нового образа
- Пользователи, включая владельца, остаются без пароля и входят по ссылке, пока не зададут его сами
- Адрес в новой таблице лежит не дольше 15 минут, как в `login_email_sends`

Откат: `rollback.sh` на прошлый образ, базу восстанавливать не нужно. Прошлая версия не знает `login_password_attempts` и не читает пароли из `accounts`. Заданные пароли сохранятся и снова заработают при возврате на новую версию. Уже сменённая почта остаётся новой: старая версия входит по ней по ссылке как обычно.

### 11. Тесты

**Vitest, без моков, Mailpit и настоящая база.** `src/test/password-hash.test.ts`, `password-login.test.ts`, `password-reset.test.ts`, `settings-password.test.ts`, `settings-email.test.ts`; расширяются `login.test.ts`, `login-logs.test.ts`. Сроки проверяются сдвигом `expires_at` и `attempted_at` в базе, как в тестах входа. Письма сброса уходят в фоне, поэтому нужен помощник `waitForEmailTo(address)` в `src/test/mailpit.ts`. Сбой почты — `SMTP_URL` на закрытый порт. Прямой запрос — через `auth.handler(new Request(...))`.

**e2e — один новый сквозной** `e2e/password-login.spec.ts`: вкладка ссылки открыта сразу → вход по ссылке → клик по почте → «Настройки» → задать пароль → выйти → вкладка «Почта и пароль» → вход по паролю → вкладка запомнилась → «Забыли пароль?» → письмо → новый пароль → вход → смена почты → вход с новой почтой. Существующие: вкладка ссылки открыта сразу, поэтому `e2e/sign-in.ts` не меняется, если в браузере теста нет cookie `login_method`; `e2e/login.spec.ts` проверяет обновлённую страницу входа и текст вкладок. Проверки не удаляются, меняются только под новое требование.

Сценарии чисто экранного поведения вне этого пути (показ пароля, сохранение почты при переключении, вёрстка) проверяются руками: так договорено для фич вне главного пути.

### 12. Смена почты

Схема рынка (Notion, Slack, OWASP): текущий пароль, ссылка на новую почту, уведомление на старую.

Better Auth не проверяет пароль на `/change-email`, поэтому единственный вход — server action. `hooks.before` отклоняет `/change-email` и `/send-verification-email`, если запрос пришёл по HTTP (`ctx.request` задан): иначе украденная сессия меняла бы почту без пароля, а второй путь позволял бы слать письма в обход лимита. Вызов `auth.api` с сервера этот запрет проходит.

`requestEmailChange(formData)` в `src/app/(app)/settings/actions.ts`:

1. `requireUserId`, `getCurrentUser`, `loginEmailSchema` для новой почты; неверная — «Проверьте адрес почты»; совпала с текущей — «Это ваша текущая почта»
2. `hasPassword`: пароля нет — отказ. На экране форма в этом случае не показывается
3. `reservePasswordAttempt(текущая почта)`, `auth.api.verifyPassword`; неверный — «Неверный текущий пароль»; верный — `clearPasswordAttempts`
4. Резервирование письма в `login_email_sends` для новой почты; сверх лимита — «Слишком часто…»
5. `auth.api.changeEmail({ body: { newEmail, callbackURL: "/login/email-changed" }, headers })`
6. `sendInBackground(sendEmailChangeNotice(текущая почта, новая почта))`

Шаг 4 идёт для занятой и свободной почты одинаково, поэтому лимит занятость не выдаёт. Шаг 6 — при запросе, а не при переходе по ссылке: после смены `afterEmailVerification` получает уже нового пользователя, а старый адрес лежит только в токене; и владельцу полезнее узнать до смены.

`sendEmailChangeLink({ user, url })` — обычный фоновый `sendInBackground`. Better Auth подставляет новую почту в `user.email`.

`src/app/login/email-changed/page.tsx` — публичная страница-развилка: есть `error` → «Ссылка устарела», «Откройте настройки и запросите смену почты заново.», ссылка «В настройки»; ошибки нет и вход есть → `redirect("/settings?email=changed")`, где показывается «Почта изменена»; ошибки нет и входа нет → `redirect("/login?email=changed")`, где показывается «Почта изменена. Войдите с новой почтой.» Публичная, потому что `/settings` без входа ушла бы на страницу входа и потеряла причину.

После смены почты ссылки смены пароля этого человека удаляются в `emailVerification.afterEmailVerification`: они ушли на старую почту, а её обычно меняют, когда ящик потерян или взломан. Better Auth вызывает этот обработчик только при `email_verified = true`; такое значение у всех пользователей (см. Context). Хук `hooks.after` для `/verify-email` не подходит: и удача, и отказ там выглядят как редирект.

Своё создание сессии после перехода по ссылке не добавляется: Better Auth убрал его в 1.7.16, решение владельца — страница входа с сообщением.

Альтернативы:

- Подтверждение с обеих почт (`sendChangeEmailConfirmation`) — готово в Better Auth и строже, но без доступа к старой почте сменить её нельзя; OWASP советует его для систем высокого риска. Отвергнуто владельцем
- Запись токена в базу, чтобы новая ссылка гасила прежнюю — лишний код: первая открытая ссылка всё равно гасит остальные

## Risks / Trade-offs

- [Хэш занимает 128 МБ на расчёт, в пуле 4 потока, пик около 512 МБ при наплыве запросов] → лимит IP и блокировка до расчёта. На сервере 1,8 ГБ, свободно 1,1 ГБ, подкачка 899 МБ (проверено 5 ноября), пик укладывается. Если после выкатки памяти окажется мало, берётся `N=2^15, r=8, p=3` (32 МБ, та же стойкость по OWASP), уже сохранённые пароли продолжат проверяться
- [Минимум 8 символов без проверки по утечкам: популярные пароли возможны] → решение владельца; подбор сдерживают 5 попыток на почту, а уведомление сообщает о смене пароля
- [Письмо сброса потерялось при сбое почты, человек думает, что оно ушло] → ошибка в логе; вход по ссылке работает как запасной путь и показывает сбой на экране. Выбрано ради защиты от перебора адресов
- [Чужой подбор блокирует вход по паролю на 15 минут] → вход по ссылке работает, блокировка в тексте ошибки объяснена
- [Запросы «Забыли пароль?» на чужую почту расходуют лимит писем, и владелец почты на 10 минут не получит ссылку] → такое уже возможно и со ссылками входа; лимит короткий и защищает ящик от рассылки
- [Украденная сессия позволяет задать первый пароль, а затем сменить почту] → письма «Пароль изменён» и «Запрошена смена почты» на старую почту. Защита зависит от того, заметит ли их владелец; принято осознанно: это стандартная схема
- [Смену почты сделал чужой человек, и ссылка уже открыта] → из приложения не вернуть: владелец правит `users.email` на сервере
- [После смены старая почта свободна: вход по ссылке на неё создаёт нового пустого пользователя] → следствие правила «первый вход — регистрация»
- [Сменили почту из `OWNER_EMAIL`] → `pnpm db:seed` выдаёт понятную ошибку, пока `.env` не обновлён; на саму работу приложения не влияет
- [Новую почту заняли между запросом и переходом по ссылке] → запись упрётся в уникальность почты, смена не пройдёт, данные целы; редкий случай, отдельного экрана нет
- [Токен сброса виден в журналах nginx и истории браузера, как и ссылка входа] → одноразовый, живёт 15 минут и гаснет при использовании
- [Внутренние форматы Better Auth — хэш токена и `value = user.id` — изменятся при обновлении] → их ловят тесты «новая ссылка гасит старую» и «ссылки нет в базе»
- [Письма в фоне теряются при перезапуске контейнера в момент выкатки] → окно в доли секунды; человек запросит заново
- [В браузере есть вход другого пользователя, и он сбрасывает пароль: `/login` отправит его на главную под тем входом] → редкий случай, пароль при этом изменён верно

## Migration Plan

1. Обычная выкатка: merge → образ → бэкап → миграции → новый образ → smoke `/health`. Новых строк в `.env` нет, действий человека на сервере нет
2. После выкатки: войти по ссылке → клик по почте → задать пароль → выйти → войти по паролю → письмо «Пароль в Личной CRM изменён» пришло
3. Проверить память приложения при входе: `docker stats` на сервере
4. Откат — `rollback.sh`, база остаётся
