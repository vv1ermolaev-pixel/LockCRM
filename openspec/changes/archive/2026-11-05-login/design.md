# Design

## Context

Требования — `specs/user-login`, `specs/data-ownership`, `specs/contact-groups` этого изменения; зачем — `proposal.md`.

Как сейчас:

- Пользователей нет. Таблицы `contacts`, `notes`, `groups`, `contact_groups` (`src/db/schema.ts`) общие для всех, кто открыл адрес
- Доступ к базе — функции в `src/lib/contacts.ts`, `groups.ts`, `keep-in-touch.ts`, `contacts-page.ts` и server actions в `src/app/actions.ts`. Ни одна не знает, кто спрашивает
- Миграция `0003_default_groups.sql` вставляет 4 группы без владельца — они есть в любой базе, в том числе в свежей базе тестов и CI
- Уникальность названия группы — индекс `groups_name_key_idx` по `replace(lower(name), 'ё', 'е')` на всю таблицу
- Vitest вызывает server actions напрямую; `next/cache` подменён заглушкой (`vitest.config.mts`). Каждый тест начинается со свежей базы: схемы удаляются, все миграции применяются заново (`src/test/database.ts`)
- e2e вставляют данные SQL-запросами прямо в базу и проверяют счётчики по всей таблице `contacts`
- Миграции: `pnpm db:migrate` (drizzle-kit) локально и в CI, `scripts/migrate.ts` в разовом контейнере на сервере
- Next.js 16: middleware теперь называется Proxy (`src/proxy.ts`), годится только для быстрой проверки, не для настоящей авторизации
- Репозиторий публичный: личные данные владельца (его почта) в git попасть не должны
- Better Auth 1.7.x (проверено по пакету): плагин magic link хранит ссылку в таблице проверок с почтой в JSON (`{"type":"magic-link","email":…}`), гасит ссылку при первом входе, срок настраивается (`expiresIn`), хранение хэша (`storeToken: "hashed"`), при ошибке ведёт на `errorCallbackURL?error=…`. Гасить старые ссылки при новом запросе и лимит писем на почту он сам не умеет

## Goals / Non-Goals

**Goals:**

- Проверка «кто спрашивает» на сервере в каждом запросе к данным, а не в интерфейсе
- Одна точка, где запрос к данным получает пользователя: забыть фильтр по владельцу трудно, а тест ловит
- Миграция переносит данные владельцу атомарно: либо всё, либо ничего
- Тесты проходят настоящий вход (письмо в Mailpit → ссылка → сессия), без моков

**Non-Goals:**

- Защита строк на уровне Postgres (Row Level Security) — избыточно для одного приложения с одним пользователем базы
- Проверка на уровне базы, что контакт и группа в `contact_groups` одного владельца (составные внешние ключи) — проверяет код, ловят тесты
- Свой интерфейс для просмотра сессий, удаление аккаунта

## Decisions

### 1. Better Auth + плагин magic link, таблицы во множественном числе

`betterAuth()` в `src/lib/auth.ts` с `drizzleAdapter(db, { provider: "pg", usePlural: true })`: таблицы `users`, `sessions`, `accounts`, `verifications` — по-английски во множественном числе, как `contacts`, `notes`, `groups`. Схема таблиц пишется в `src/db/schema.ts` по документации Better Auth для установленной версии; миграция — через drizzle-kit, как остальные.

Настройки:

- `magicLink({ expiresIn: 15 * 60, storeToken: "hashed", sendMagicLink })` — 15 минут, в базе только хэш ссылки
- `session: { expiresIn: 30 дней, updateAge: 1 день }` — срок продлевается при заходе, не чаще раза в сутки (иначе запись в базу на каждый запрос)
- `rateLimit` встроенный, для `/sign-in/magic-link` — 30 запросов в минуту с одного IP (защита от рассылки на тысячи адресов). Хранение в памяти: один контейнер приложения. За nginx IP берётся из `X-Forwarded-For` (его ставит `proxy_params`)
- `nextCookies()` — чтобы `signOut` из server action стирал cookie
- Маршрут `src/app/api/auth/[...all]/route.ts` через `toNextJsHandler(auth)`

Создание `auth` ленивое, при первом обращении — как `db` в `src/db/index.ts`: сборка образа загружает модули без настроек, и `betterAuth()` не должен падать без `BETTER_AUTH_SECRET` во время `next build`.

Альтернативы: свой вход на токенах — больше кода и рисков, а Better Auth уже в стеке (CLAUDE.md).

### 2. Почта проверяется до Better Auth, одна функция на форму и прямой запрос

`hooks.before` на путь `/sign-in/magic-link`: обрезать пробелы, привести к нижнему регистру, проверить zod-схемой `loginEmailSchema` (`src/lib/validation.ts`). Неверная — `APIError` 400, письмо не уходит. Верная — подменяет `body.email` нормализованной. Так прямой запрос на `/api/auth/sign-in/magic-link` проходит ту же проверку, что и форма.

Форма — server action `requestLoginLink(formData)` в `src/app/login/actions.ts`: та же `loginEmailSchema` для ошибки под полем, потом `auth.api.signInMagicLink({ body: { email, callbackURL: "/", errorCallbackURL: "/login/expired" }, headers })`. Ошибки Better Auth переводятся в ответ формы: лимит (429) → «Слишком часто, попробуйте через несколько минут»; сбой отправки → «Не удалось отправить письмо. Попробуйте ещё раз.»; успех → `{ ok: true, email }` с нормализованной почтой.

Одна клиентская форма `LoginForm` (`src/components/login-form.tsx`) на двух страницах, разные только заголовок, текст, подпись кнопки и начальное значение поля. Ошибки — под полем, форма на месте. Успех — форма сменяется экраном «Проверьте почту» (значок письма, «Отправили ссылку для входа на <почта>. Ссылка работает 15 минут.», кнопка «Ввести другую почту»). «Ввести другую почту» возвращает форму с той же почтой в поле — без запроса к серверу.

Better Auth сам ищет пользователя по почте в том виде, в каком она пришла; так как в базу попадает только нормализованная почта, «Anna@Example.com» и «anna@example.com» — один пользователь.

### 3. Лимит писем и гашение старых ссылок — внутри `sendMagicLink`, под блокировкой по почте

Новая таблица `login_email_sends (id, email, sent_at)`, индекс `(email, sent_at)`.

`sendMagicLink({ email, url })` делает в одной транзакции:

1. `pg_advisory_xact_lock(hashtext(email))` — два одновременных запроса на одну почту идут по очереди, четвёртое письмо не проскочит
2. Удаляет записи `login_email_sends` старше 10 минут (почта хранится не дольше нужного)
3. Считает письма на эту почту за 10 минут; 3 и больше — `APIError` 429 `TOO_MANY_LOGIN_EMAILS`
4. Удаляет из `verifications` прежние ссылки этой почты (`value::jsonb->>'type' = 'magic-link'` и та же почта), кроме только что созданной (самой новой по `created_at`), и все просроченные строки
5. Отправляет письмо; записывает строку в `login_email_sends`
6. Ошибка отправки — откат транзакции: письмо не засчитано, старые ссылки живы; `APIError` 502 `LOGIN_EMAIL_FAILED`

Письмо отправляется внутри транзакции и держит блокировку секунды — для такой нагрузки это нормально.

Альтернативы: проверка лимита в `hooks.before`, а запись после отправки — между ними может проскочить лишнее письмо; встроенный rateLimit Better Auth — считает по IP и пути, не по почте.

Риск: формат строки в `verifications` — внутренность Better Auth. Его ловит тест «новая ссылка гасит старую»; версию Better Auth обновлять вместе с прогоном тестов.

### 4. Устаревшая ссылка и «Отправить ссылку повторно»

`errorCallbackURL = "/login/expired"`. Better Auth ведёт туда при любой ошибке проверки (`INVALID_TOKEN`, `EXPIRED_TOKEN` и т. п.). Страница `src/app/login/expired/page.tsx` одна для всех причин: значок `Link2OffIcon` (lucide, разорванная ссылка), «Ссылка устарела», «Запросите новую — она придёт на почту.» и та же `LoginForm` с кнопкой «Отправить ссылку повторно». Она вызывает тот же `requestLoginLink`, поэтому проверка почты, лимит и гашение старых ссылок те же.

Почта для подстановки. Ни ссылка, ни её строка в базе почту не отдадут: строка удалена после входа или просрочки, в базе только хэш. Поэтому `requestLoginLink` после успешной отправки ставит cookie `login_email`: почта, `httpOnly`, `SameSite=Lax`, `Secure` на сервере, `path=/login`, 7 дней. Страница «Ссылка устарела» (серверный компонент) читает её и подставляет в поле. Нет cookie (письмо открыли в другом браузере, прошло больше 7 дней) — поле пустое.

Альтернативы:

- Почта в адресе `errorCallbackURL` — попадает в ссылку письма и в журналы nginx: личные данные в логах. Отвергнуто
- Непрозрачный номер запроса в адресе и почта в базе по нему — почту пришлось бы хранить дольше 10 минут, а выигрыш тот же. Отвергнуто
- Кнопка ведёт на `/login` — «отправить повторно» обещает больше, чем делает. Отвергнуто владельцем

### 5. Письма: Nodemailer, транспорт из настройки `SMTP_URL`

`src/lib/mail.ts`: `nodemailer.createTransport(process.env.SMTP_URL)`, `sendLoginEmail(to, url)`. Отправитель `"Личная CRM" <${MAIL_FROM}>`, тема «Вход в Личную CRM». Письмо в двух видах — HTML и обычный текст (его показывают почтовые программы, которые не умеют HTML; в нём вместо кнопки сама ссылка). Текст короткий, по образцу писем входа у Slack и Notion:

1. «Чтобы войти в Личную CRM, перейдите по ссылке. Ссылка работает 15 минут.»
2. Кнопка «Войти»
3. «Если вы не запрашивали вход — просто проигнорируйте письмо.» — мелким серым

- Локально и в CI: `SMTP_URL=smtp://127.0.0.1:1025` — Mailpit
- На сервере: `SMTP_URL=smtps://resend:<ключ>@smtp.resend.com:465` — Resend по SMTP

Одна сборка, разница только в `.env`. Отдельный SDK Resend не нужен: Nodemailer шлёт в него по SMTP.

В HTML письма стили инлайном: почтовые программы не понимают CSS-переменные и классы Tailwind. Цвета берутся из значений дизайн-токенов (`src/app/tokens.css`) — исключение из правила «только через токены», записать в комментарии.

### 6. Кто спрашивает: `src/lib/session.ts`

- `getCurrentUser()` — `auth.api.getSession({ headers: await headers() })`, обёрнута в React `cache()`: один запрос к базе на рендер
- `requireUserId()` — нет сессии → `redirect("/login")`

Каждая функция доступа к данным получает `userId` первым параметром: `listFirstContacts(userId, …)`, `getContact(userId, id)`, `listGroups(userId)`, `listDueContacts(userId, …)` и т. д. Страницы и server actions сначала вызывают `requireUserId()`. Ни одна функция в `src/lib` сама не читает сессию — так её можно тестировать с любым пользователем.

Правила фильтра:

- `contacts`, `groups` — `owner_id = userId` в каждом `select`, `update`, `delete`
- `notes` — только через свой контакт: `addNote` блокирует контакт с условием `id и owner_id`; `listNotes` — join с `contacts`
- `contact_groups` — `setContactGroups` берёт только группы этого владельца (`groups.owner_id = userId`), `contactInGroup` — только своя группа
- Поиск, счётчики, «Пора связаться», порядок групп, создание группы из окна контакта — с тем же условием
- Чужой номер даёт тот же ответ, что отсутствующий: `contactDeleted` в actions, `notFound()` на карточке, «нет фильтра» для чужой группы в адресе

### 7. Proxy — только быстрый отсев, настоящая проверка на сервере

`src/proxy.ts`: нет cookie сессии (`getSessionCookie` из `better-auth/cookies`) → редирект на `/login`. Пропускает `/login`, `/login/expired`, `/api/auth/*`, `/health`, файлы `/_next/*`, `favicon.ico`. Cookie есть, но сессия просрочена — Proxy пропускает, а `requireUserId()` на странице или в action отправит на `/login`.

Страница `/login` при живой сессии делает `redirect("/")`.

### 8. Маршруты и шапка

- Страницы приложения переезжают в группу маршрутов `src/app/(app)/` (`page.tsx`, `contacts/[id]/…`); адреса не меняются
- `src/app/(app)/layout.tsx` — шапка: логотип, почта пользователя, кнопка «Выйти»
- `src/app/layout.tsx` — только `html`, шрифты, `Toaster`
- `src/app/login/layout.tsx` — логотип по центру, без почты и «Выйти»
- Значки на экранах входа — из lucide-react, как в остальных пустых состояниях приложения (`UserXIcon`, `UsersIcon`): `MailCheckIcon` на «Проверьте почту», `Link2OffIcon` на «Ссылка устарела». Эмодзи не используются
- Тексты страницы входа: заголовок «Вход в приложение», «Введите почту — пришлём ссылку для входа. Пароль не нужен.», поле «Почта», кнопка «Получить ссылку для входа»
- «Выйти» — server action `signOut`: `auth.api.signOut({ headers })` удаляет только сессию этого устройства. Затем полная навигация на `/login` (`window.location.replace`), чтобы клиентский кэш роутера не показал контакты по «Назад»

### 9. Готовые группы нового пользователя

Список 4 групп переезжает в код: `defaultGroups` в `src/lib/groups.ts` (те же названия, цвета, порядок, что в `0003_default_groups.sql`). `databaseHooks.user.create.after` создаёт их новому пользователю. Владельцу при миграции их не создаём: у него остаются его существующие группы.

### 10. Почта владельца: настройка окружения, параметр разовой миграции данных

Почта владельца — это не код и не схема, а значение для конкретной установки, к тому же личные данные. Поэтому:

- **Где живёт**: только в `.env` той установки, где есть данные без владельца, — `/srv/lockcrm/.env` на сервере (права 600) и `.env` на компьютере владельца. В git, в SQL миграции, в спеках и в обзорах её нет: репозиторий публичный. В CI её нет: там база пустая
- **Кто читает**: только запуск миграций (`scripts/migrate.ts`) и демо-данные (`scripts/seed.ts`). Приложение во время работы её не знает и не сравнивает почту вошедшего с ней: после переноса владелец — обычный пользователь, никаких особых прав
- **Как попадает в миграцию**: SQL-миграция Drizzle не читает окружение, поэтому `scripts/migrate.ts`:
  1. Читает `OWNER_EMAIL`, если она задана: обрезает пробелы, переводит в нижний регистр, проверяет той же `loginEmailSchema`. Неверная — падает до миграций
  2. На своём единственном соединении делает `set_config('app.owner_email', <почта>, false)` — параметр живёт только в этом соединении и нигде не сохраняется
  3. Применяет миграции; SQL читает почту через `current_setting('app.owner_email', true)`
- **Когда нужна**: один раз — когда миграция `0004` переносит существующие данные. После этого настройка ничего не делает (миграция уже применена), её можно оставить для `pnpm db:seed` или убрать. Новая установка на пустую базу её не требует (решение 11)

`pnpm db:migrate` переходит с drizzle-kit на `tsx --env-file-if-exists=.env scripts/migrate.ts` — тот же скрипт, что на сервере (таблица учёта миграций та же).

Отвергнутые варианты:

- Почта в SQL миграции или в коде — личные данные в публичном репозитории, а для каждой установки своя почта
- «Первый вошедший получает всё» — первым может войти друг
- Отдельный ручной скрипт переноса после выкатки — между выкаткой и запуском скрипта данные без владельца, поле владельца нельзя сделать обязательным сразу, нужны две выкатки
- Сделать `OWNER_EMAIL` обязательной всегда (в CI, тестах, на каждой новой машине) — разовая операция превращается в вечное требование. Это и есть костыль, которого избегаем

### 11. Миграции

**`0004_users_and_owners`** — сгенерирована drizzle-kit из схемы и вручную дописана, чтобы не упасть на непустых таблицах. Всё в одной транзакции мигратора:

1. Создаёт `users`, `sessions`, `accounts`, `verifications` (по схеме Better Auth), `login_email_sends`
2. Добавляет `owner_id text` (пока без `NOT NULL`) в `contacts` и `groups`
3. Блок `DO $$ … $$` решает, кому отдать существующие строки:
   - почта задана → создаёт пользователя `users(id = gen_random_uuid()::text, name = '', email, email_verified = true)`, если его нет; `update contacts/groups set owner_id = <его id> where owner_id is null`
   - почта не задана, и в базе только 4 нетронутые готовые группы из `0003` (те же названия, цвета, порядок, ни одного участника) и ни одного контакта — это новая установка: эти 4 группы удаляются, пользователей не создаётся. Каждый пользователь получит свои 4 группы при первом входе (решение 9)
   - почта не задана, а данные есть (хоть один контакт, участие в группе или группа, отличная от готовых) → `RAISE EXCEPTION 'OWNER_EMAIL is not set: existing contacts and groups need an owner'`
4. `owner_id` → `NOT NULL`, внешний ключ на `users(id)` **без каскада** (`on delete restrict`): данные не могут пропасть вместе с пользователем
5. Индексы: `groups_name_key_idx` пересоздаётся как `(owner_id, replace(lower(name), 'ё', 'е'))`; `contacts_name_idx` → `(owner_id, name)`; новый `groups (owner_id, position)`

Что происходит с существующей базой на сервере:

- Контакты, заметки, группы, участия в группах не меняются по содержанию и количеству; у контактов и групп появляется `owner_id` = id владельца. Заметки и `contact_groups` не трогаются
- Появляется один пользователь — владелец, с почтой из `OWNER_EMAIL`. Когда он входит по ссылке, Better Auth находит его по почте
- Падение на любом шаге — откат всей транзакции: база как до выкатки, новый образ не стартует (`deploy.sh`), работает прежняя версия

Свежая база (CI, тесты, новый компьютер): после `0003` в ней только 4 нетронутые группы без владельца — миграция удаляет их, `OWNER_EMAIL` не нужна.

Тест миграции: `resetTestDatabaseUpTo("0003_default_groups")`, вставить контакты, заметки, группы, участия → `applyPendingMigrations` с почтой → всё на месте и у владельца; та же база без почты — ошибка и база без изменений; свежая база без почты — проходит, групп и пользователей нет; свежая база с почтой — владелец с 4 группами.

Альтернатива: «первый вошедший получает всё» — опасно, первым может войти друг. Альтернатива: почта прямо в SQL — видна в публичном репозитории.

### 12. Демо-данные

`scripts/seed.ts` находит пользователя по `OWNER_EMAIL` (после миграции он есть) и создаёт контакты и группы с его `owner_id`. Проверка «уже есть контакты — ничего не делать» считает контакты этого владельца. Нет `OWNER_EMAIL` или пользователя — ошибка с понятным текстом, ничего не меняется.

### 13. Настройки (`.env`)

| Строка | Где | Значение |
| --- | --- | --- |
| `BETTER_AUTH_SECRET` | везде | случайная строка ≥ 32 символов; на сервере генерирует человек |
| `BETTER_AUTH_URL` | везде | `http://localhost:3000` локально, `http://127.0.0.1:3000` в CI, `https://app.funkicrm.ru` на сервере |
| `SMTP_URL` | везде | Mailpit локально и в CI, Resend на сервере (с ключом — секрет) |
| `MAIL_FROM` | везде | адрес отправителя, на сервере — на подтверждённом в Resend домене |
| `OWNER_EMAIL` | сервер и компьютер владельца — там, где есть данные без владельца; для seed | почта владельца; в CI не нужна |
| `MAILPIT_URL` | тесты | `http://127.0.0.1:8025` по умолчанию |

`.env.example` — те же строки без значений, у `OWNER_EMAIL` комментарий: нужна только для переноса существующих данных и для seed. `deploy/compose.yaml`: `app` получает `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, `MAIL_FROM` (через `${…:?…}` — без них приложение не работает); `migrate` — `DATABASE_URL` и `OWNER_EMAIL` как необязательную (`${OWNER_EMAIL:-}`): нужна ли она, решает сама миграция, и без неё на базе с данными падает целиком, ничего не меняя.

### 14. Тесты

**Mailpit** — в `compose.yaml` (порты только на `127.0.0.1`: SMTP 1025, страница 8025) и сервисом в задаче `tests` в CI. Образ — последняя стабильная версия `axllent/mailpit`, проверить при реализации.

**Vitest**: `next/headers` подменяется заглушкой `src/test/stubs/next-headers.ts` (как `next/cache`): она отдаёт заголовки «текущего браузера», которые выставляет тест. Помощник `signInAs(email)` проходит настоящий вход: `auth.api.signInMagicLink` → письмо в Mailpit → ссылка из письма → `auth.api.magicLinkVerify` → cookie сессии кладётся в заглушку. Сроки (16 минут, 10 минут, 31 день) проверяются сдвигом времени в базе (`expires_at`, `sent_at`), без поддельных часов. Сбой отправки — `SMTP_URL` на закрытый порт внутри теста.

Существующие тесты: `addContact`, `addGroup` и прямые вызовы `src/lib/*` получают пользователя; в начале каждого — `signInAs` тестового пользователя.

**e2e**: помощник `e2e/sign-in.ts` — ввести почту на `/login`, взять ссылку из Mailpit по адресу получателя, открыть. Каждый файл входит под своей уникальной почтой (`e2e-<файл>-<время>@example.com`): у него свои данные, счётчики не пересекаются. SQL-вставки в e2e получают `owner_id` этого пользователя. Новый `e2e/login.spec.ts` — критерий успеха A/B из спеки и основные экраны входа. `main-scenario.spec.ts` входит под пользователем перед сценарием, шаг «другой браузер» входит под той же почтой.

### 15. Логи без личных данных

Ошибки отправки письма и Better Auth логируются без адреса почты и ссылки: `sendMagicLink` ловит ошибку Nodemailer и пишет только код ошибки. `logger` Better Auth — уровень `error`; при реализации проверить каждую ветку сбоя (неверная почта, лимит, сбой SMTP, просроченная ссылка) на то, что попадает в лог.

## Risks / Trade-offs

- [Откат на прошлую версию после выкатки ломает данные: старый код не знает `owner_id`, а `NOT NULL` не даст ему создать контакт] → откат только вместе: `deploy/rollback.sh` на прошлый образ и `deploy/restore.sh` с копией, снятой перед выкаткой (`*_deploy_<прошлая версия>.dump`). Описать в README
- [`OWNER_EMAIL` забыли на сервере] → в базе есть контакты, поэтому миграция падает с `RAISE EXCEPTION` и откатывается целиком; новый образ не стартует, работает прежняя версия. Бэкап к этому моменту уже снят — лишний файл, не вред
- [Удаление 4 готовых групп на «пустой» базе задело бы чьи-то данные] → удаляются только при нуле контактов, нуле участий и полном совпадении названий, цветов и порядка с `0003`; любая правка групп — и миграция требует почту. На сервере контакты есть, ветка удаления там не срабатывает
- [Опечатка в `OWNER_EMAIL`] → данные уйдут пользователю с чужой почтой, войти в него нельзя. Перед выкаткой владелец сверяет строку; исправление — `update users set email = … where email = …` на сервере, ничего не теряется
- [Внутренний формат `verifications` Better Auth изменится] → тест «новая ссылка гасит старую» упадёт при обновлении
- [Письмо внутри транзакции держит соединение] → при недоступном SMTP — таймаут Nodemailer, задать небольшой (10 секунд)
- [Лимит по IP в памяти сбрасывается при перезапуске] → приемлемо; лимит на почту в базе не сбрасывается
- [Proxy пропускает просроченную cookie] → настоящая проверка в `requireUserId()` на каждой странице и в каждом action
- [Пропустить `owner_id` в новом запросе в будущем] → `userId` — обязательный параметр каждой функции доступа; тесты «чужое не видно» для каждого экрана
- [Письма от Resend в спаме, пока домен не подтверждён] → домен и DNS-записи (SPF, DKIM) — шаг человека до выкатки
